## Executive Summary

The security scan identified **5 critical/high-risk vulnerabilities** that require immediate attention. The most significant finding is a **Broken Access Control** in the video listing API, which allows any user to view any other user's data. Additionally, the GPU API is vulnerable to **SSRF**, and the frontend authentication logic is easily bypassable.

## Detailed Findings

### 1. [CRITICAL] Broken Access Control in Video Listing

- **Location:** `web/app/api/videos/route.ts:GET`
- **Risk:** Data Breach (Full exposure of all users' video projects)
- **Description:** The endpoint takes a `userId` query parameter and queries the database using a `service role client`. It does **not** verify if the requested `userId` matches the authenticated user's ID.
- **Impact:** An attacker could iterate through UUIDs or discover a user's ID and fetch their entire project list, including metadata and titles.
- **Remediation:**
  - Call `getAuthenticatedUser()` within the `GET` handler.
  - Filter the query by the authenticated user's ID instead of the query parameter.

### 2. [HIGH] Server-Side Request Forgery (SSRF)

- **Location:** `Vid-Bolt-GPU-API/app/services/storage.py:StorageService.download_from_url`
- **Risk:** Internal Network Exposure / Data Exfiltration
- **Description:** The GPU API downloads files from arbitrary URLs provided in request bodies. It does not validate the URL against a blocklist or whitelist.
- **Impact:** An attacker could force the server to fetch sensitive metadata from the cloud provider (e.g., `169.254.169.254`) or scan the internal network (e.g., `localhost:8000`).
- **Remediation:**
  - Implement URL validation to block private/internal IP ranges (RFC 1918).
  - Restrict downloads to known allowed domains if possible.

### 3. [HIGH] Weak Authentication Bypass in Middleware

- **Location:** `web/middleware.ts`
- **Risk:** Authentication Bypass
- **Description:** The middleware's redirect logic relies on checking the `is_logged_in` cookie for a value of `true`.
- **Impact:** Users can manually set this cookie in their browser to bypass the middleware redirect for most pages. Although `updateSession` refreshes the token, it does not currently block access if the session is invalid at the middleware level.
- **Remediation:**
  - Modify `middleware.ts` to rely solely on the result of `supabase.auth.getUser()` for redirect decisions.
  - Remove reliance on plain-text client-side cookies for security gates.

### 4. [MEDIUM] Public Webhook Callback Spoofing

- **Location:** `web/app/api/gpu-callback/route.ts`
- **Risk:** Data Integrity / System Manipulation
- **Description:** Signature verification is skipped if `GPU_WEBHOOK_SECRET` is not configured.
- **Impact:** If a deployment forgets to set the secret, an attacker can POST fake "completed" results with malicious URLs or data, manipulating the processing state of user videos.
- **Remediation:**
  - "Fail closed": Require the secret to be present unless a specific `NODE_ENV=development` flag is set.
  - Warn if the secret is missing during application startup.

### 5. [MEDIUM] Missing Rate Limiting

- **Location:** Global (GPU API & Next.js API)
- **Risk:** Denial of Service (DoS) / Cost Exploitation
- **Description:** There is no evidence of rate limiting on expensive generation endpoints.
- **Impact:** An attacker could flood the API with generation requests, leading to high GPU costs or system exhaustion.
- **Remediation:**
  - Implement rate limiting using Redis/BullMQ or a dedicated middleware like `fastapi-limiter`.

## Technical Recommendations

### GPU API Security Hardening

1.  **Block Internal IPs:** Use a library like `ipaddress` to verify the URL target is not private.
2.  **API Key Entropy:** Ensure the `X-API-Key` is a long, cryptographically secure string in production.

### Web/Supabase Hardening

1.  **Row Level Security (RLS):** While you are using a service role client in the API routes, ensure that **RLS is enabled** on all Supabase tables as a second layer of defense.
2.  **JWT Validation:** Ensure all API routes that access user data validate the JWT via `supabase.auth.getUser()`.
