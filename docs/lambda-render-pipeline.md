# Remotion Lambda Render Pipeline

Comprehensive guide for the AWS Lambda-based video rendering system. This pipeline transforms Video Editor V2 compositions into rendered MP4 files using Remotion Lambda, with final output stored on Cloudflare R2.

## Architecture Overview

```
Client (Browser)
    │
    ▼
POST /api/render          ← Auth + rate limit + serialize + enqueue
    │
    ▼
BullMQ Queue              ← "video-render" queue (Redis-backed, FIFO)
    │
    ▼
Render Worker             ← Validates, starts Lambda, polls progress
    │
    ▼
Remotion Lambda           ← 200 Lambda functions render chunks in parallel
    │
    ├── S3 (temp)         ← Intermediate chunk files (auto-deleted after 1 day)
    │
    └── Cloudflare R2     ← Final stitched MP4 (permanent storage)
    │
    ▼
GET /api/render/progress  ← Client polls for status → returns done + URL
```

### Key Components

| Component              | Description                                                                  |
| ---------------------- | ---------------------------------------------------------------------------- |
| **Remotion Lambda**    | Distributes video rendering across up to 200 AWS Lambda functions per render |
| **BullMQ**             | Redis-backed job queue managing render concurrency and retries               |
| **S3**                 | Temporary storage for Remotion's intermediate chunk files                    |
| **Cloudflare R2**      | Final destination for rendered MP4 files (uses your existing bucket)         |
| **Webhook (optional)** | Lambda can call back to `/api/render/webhook` on completion                  |

## Initial Setup

### 1. Install Dependencies

```bash
cd web
npm install @remotion/lambda
```

Already done — `@remotion/lambda@^4.0.417` is in `package.json`.

### 2. Set AWS Credentials

Add to `.env.local`:

```env
AWS_ACCESS_KEY_ID=your_access_key
AWS_SECRET_ACCESS_KEY=your_secret_key
REMOTION_AWS_REGION=us-east-1
```

### 3. Deploy Lambda Infrastructure

```bash
npx tsx scripts/deploy-lambda.ts
```

This script:

1. Creates an S3 bucket in your region (or reuses existing)
2. Bundles your Remotion composition and uploads it to S3
3. Creates the Lambda function with configured RAM/disk/timeout

On success, it prints 4 values — paste them into `.env.local`:

```env
REMOTION_AWS_REGION=us-east-1
REMOTION_FUNCTION_NAME=remotion-render-4-0-422-mem2048mb-disk10240mb-120sec
REMOTION_SERVE_URL=https://remotionlambda-useast1-xxx.s3.../sites/vidbolt-render/index.html
REMOTION_S3_BUCKET=remotionlambda-useast1-xxx
```

### 4. Apply Database Migration

```bash
npx supabase db push
```

This creates the `render_jobs` table with RLS policies.

### 5. Re-deploy After Composition Changes

Whenever you modify the Remotion composition (overlays, effects, etc.), re-run:

```bash
npx tsx scripts/deploy-lambda.ts
```

This re-uploads the bundle. The Lambda function itself doesn't need to change unless you modify RAM/disk/timeout settings.

```typescript
lambdaConfig.region; // REMOTION_AWS_REGION
```

## How Rendering Works

### Step-by-Step Flow

1. **Client calls `POST /api/render`** with composition data (overlays, dimensions, fps, etc.)
2. **API route** authenticates the user, checks rate limits, serializes/validates the input props, and enqueues a BullMQ job
3. **BullMQ worker** picks up the job (up to 4 concurrent):
   - Validates render props (no blob URLs, valid dimensions, etc.)
   - Calls `renderMediaOnLambda()` which starts 200 Lambda functions
4. **Each Lambda function** renders a chunk of frames, uploads to S3
5. **One Lambda** stitches all chunks together and uploads the final MP4 directly to Cloudflare R2 via `s3OutputProvider`
6. **Worker polls** `getRenderProgress()` every 2 seconds until done
7. **Client polls** `GET /api/render/progress?jobId=xxx` and receives a `ProgressResponse`:
   - `{ type: "progress", progress: 0.65 }` — still rendering
   - `{ type: "done", url: "https://...", size: 12345678 }` — finished
   - `{ type: "error", message: "..." }` — failed

### Temporary vs Permanent Storage

| Storage                       | Contents                                   | Lifetime                                                 |
| ----------------------------- | ------------------------------------------ | -------------------------------------------------------- |
| **S3** (`remotionlambda-*`)   | Remotion bundle + intermediate chunk files | Chunks auto-delete after 1 day                           |
| **R2** (your existing bucket) | Final rendered MP4                         | Permanent (`renders/{userId}/{videoId}/{timestamp}.mp4`) |

### Retry Behavior

- BullMQ retries failed jobs **2 times** with exponential backoff (5s, 10s)
- Completed jobs are kept for **3 days** (last 50)
- Failed jobs are kept for **14 days** (last 200)

## API Endpoints

### `POST /api/render`

Initiate a new render.

**Request Body:**

```json
{
  "videoId": "project-uuid",
  "overlays": [...],
  "durationInFrames": 900,
  "width": 1920,
  "height": 1080,
  "fps": 30,
  "src": "",
  "compositionId": "VideoComposition"
}
```

**Response:**

```json
{
  "jobId": "uuid",
  "bullmqJobId": "uuid",
  "outputKey": "renders/{userId}/{videoId}/{timestamp}.mp4",
  "payloadSizeKB": 45
}
```

**Errors:** `401` (unauthorized), `400` (missing/invalid fields), `429` (too many active renders).

### `GET /api/render/progress?jobId=xxx`

Poll render progress.

**Response (rendering):**

```json
{ "type": "progress", "progress": 0.65 }
```

**Response (done):**

```json
{
  "type": "done",
  "url": "https://r2.../renders/.../1234.mp4",
  "size": 15000000
}
```

**Response (failed):**

```json
{ "type": "error", "message": "Lambda render failed: Out of memory" }
```

### `POST /api/render/webhook`

Optional Remotion Lambda completion callback. Logs the event for the poll loop to pick up. Not required — polling catches completion regardless.

## Tuning & Scaling

### Concurrency Model

```
RENDER_CONCURRENCY_LIMIT × LAMBDAS_PER_RENDER = Total Lambda invocations
         4               ×       200           = 800
```

AWS default Lambda concurrency limit: **1,000**. Current config uses 800, leaving 200 buffer.

### How to Change Concurrency

| Goal                      | Change                                                                   |
| ------------------------- | ------------------------------------------------------------------------ |
| More simultaneous renders | Increase `RENDER_CONCURRENCY_LIMIT` (ensure total stays under AWS limit) |
| Faster individual renders | Increase `LAMBDAS_PER_RENDER` (more parallel chunks)                     |
| Handle more total load    | Request AWS limit increase, then raise `RENDER_CONCURRENCY_LIMIT`        |

### Lambda Resource Settings

| Setting                                   | Default | Guidance                                                                   |
| ----------------------------------------- | ------- | -------------------------------------------------------------------------- |
| **RAM** (`RENDER_LAMBDA_MEMORY_MB`)       | `2048`  | Remotion's recommended default. Increase to 3008+ for complex compositions |
| **Disk** (`RENDER_LAMBDA_DISK_MB`)        | `10240` | Maximum allowed. Minimal cost impact (<1%), enables Chrome disk cache      |
| **Timeout** (`RENDER_LAMBDA_TIMEOUT_SEC`) | `120`   | Per-chunk timeout. Increase if chunks are timing out                       |

> **Important:** After changing RAM, disk, or timeout, you must re-run `npx tsx scripts/deploy-lambda.ts` to create a new Lambda function with the updated specs. The function name changes based on these parameters.

### Per-User Rate Limiting

`MAX_RENDERS_PER_USER` (default: 3) limits how many active + waiting renders a single user can have. The API returns `429` if exceeded.

## Cost Estimation

Remotion Lambda costs are primarily AWS Lambda invocation costs:

| Component          | Approximate Cost                          |
| ------------------ | ----------------------------------------- |
| **Lambda compute** | ~$0.05–0.15 per render (30s video, 1080p) |
| **S3 storage**     | Negligible (temp chunks auto-delete)      |
| **S3 transfer**    | ~$0.01 per render                         |
| **R2 storage**     | Free egress, $0.015/GB stored             |

The render worker tracks costs via `progress.costs` and stores them in the `render_jobs` table.

## Troubleshooting

### Common Issues

| Issue                                       | Cause                                      | Fix                                                                                       |
| ------------------------------------------- | ------------------------------------------ | ----------------------------------------------------------------------------------------- |
| "Missing required env vars"                 | Deploy script checking for vars it creates | Fixed — only AWS creds + region are checked pre-deploy                                    |
| "Entry point does not contain registerRoot" | Wrong file specified                       | Entry point is `index.ts` (calls `registerRoot`), not `root.tsx`                          |
| "Bucket allows public listing"              | S3 bucket permissions                      | Follow [Remotion bucket security guide](https://remotion.dev/docs/lambda/bucket-security) |
| Lambda timeout                              | Composition too complex for chunk timeout  | Increase `RENDER_LAMBDA_TIMEOUT_SEC` and redeploy                                         |
| Out of memory                               | Composition requires more RAM              | Increase `RENDER_LAMBDA_MEMORY_MB` and redeploy                                           |
| 429 Too Many Requests                       | User hit per-user render limit             | Wait for active renders to complete or increase `MAX_RENDERS_PER_USER`                    |
| Blob URL errors                             | Editor has local blob references           | All media must be uploaded to R2 before rendering                                         |

### Database

The `render_jobs` table in Supabase tracks all render jobs:

| Column              | Description                                     |
| ------------------- | ----------------------------------------------- |
| `status`            | `queued` → `rendering` → `completed` / `failed` |
| `render_id`         | Remotion's render ID                            |
| `output_url`        | Final R2 URL of rendered video                  |
| `output_size_bytes` | File size                                       |
| `cost_accrued`      | AWS Lambda cost in USD                          |
| `error_message`     | Error details if failed                         |

RLS policies ensure users can only see their own render jobs. The service role has full access for the worker.
